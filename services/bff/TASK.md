# Шаг 13. Граница системы: экран и лимит частоты

## Что нужно сделать

Мобильный клиент показывает экран заказа: статус, товары с названиями и
ценами, состояние платежа. Данные лежат в трёх сервисах. Если клиент пойдёт
за ними сам, он заплатит тремя круговыми задержками - на плохой сети это
секунды.

BFF решает это за него: одна ручка, внутри походы к соседям.

**1. Сборка экрана.** `ScreenAssembler.assemble` в `src/screen/screen.assembler.ts`:
заказ уже прочитан, из него известны товары (`order.items`) и идентификатор
платежа (`order.paymentId`). Нужно добрать карточки товаров (`this.catalog`,
ответ `ProductCard`) и статус платежа (`this.paymentStatus`, он уже написан).
Эти походы независимы - экран не обязан ждать их по очереди, собери их через
`Promise.all`. Платежа может не быть: заказ ещё не оплачивали, и это обычное
состояние экрана (`PAYMENT_NONE`), а не ошибка.

**2. Лимит частоты.** `Limiter.check` в `src/ratelimit/limiter.ts`: считаем
запросы клиента в текущем минутном окне. Счётчик живёт в Redis, а не в памяти
процесса: экземпляров границы несколько, и лимит должен быть общим, иначе он
тихо умножается на их число. Ключ `rate:<клиент>:<номер окна>`: `incr`, на
первом попадании `expire` на окно (`WINDOW_SECONDS`) - ключ должен протухать
сам вместе с окном, отдельной чистки быть не должно. Номер окна считай от часов
сервиса (`this.clock`), а не от `Date.now()`: в тестах они заморожены. При
превышении guard отдаёт 429 и `Retry-After` (это уже написано).

## Как проверить себя

```bash
docker compose -f ../../infra/compose.yaml up -d redis
npm install
npm test
```

Только тесты, без прогона типов: `NODE_OPTIONS=--experimental-vm-modules npx jest`.

Красные: «экран собран из трёх сервисов», «экран переживает отсутствие платежа»
(экран собирается из трёх заглушек; отсутствие платежа экран не ломает) и
«четвёртый запрос за минуту получает 429 с Retry-After». Зелёные уже сейчас:
«лежащий сосед даёт 502 DOWNSTREAM_UNAVAILABLE», «неизвестный заказ это 404
ORDER_NOT_FOUND, к соседям за ним не ходим» и «квота считается на каждого
клиента» - это даётся, но после твоей правки они обязаны остаться зелёными.

Redis нужен настоящий - в этом весь смысл: счётчик общий. Тесты ходят в базу
`/1` того же Redis со стенда (`TEST_REDIS_URL`), соседи подменены заглушками
на `http.createServer`.

## На что посмотреть по дороге

- Что делать, если платежа ещё нет: заказ не оплачивали, и это нормальное
  состояние экрана, а не ошибка. Сравни с ситуацией «сервис платежей лежит» -
  ответы клиенту должны быть разными. Посмотри, как `paymentStatus` отличает
  одно от другого.
- `Promise.all` отвергается при первом отказе, но остальные походы продолжаются
  до своего ответа или таймаута: в Go `errgroup` отменял контекст соседям.
  Подумай, как сделать то же через `AbortController`, и стоит ли.
- Почему лимит считается по идентификатору клиента, а не по IP: за одним адресом
  сидит целый офис и мобильный оператор.
- Окно на минуту с фиксированной границей - самый простой вариант, и у него есть
  известный изъян: на стыке двух окон можно пройти вдвое больше. Найди этот
  сценарий и подумай, чем его лечат.
- `incr` и `expire` - две команды; между ними процесс может упасть, и ключ
  останется без срока жизни. Чем это лечат в Redis?
- Токен клиента BFF пересылает соседям как есть: кто имеет право на заказ,
  решает сервис заказов, а не граница.
- BFF это слой, а не свалка: бизнес-правил здесь быть не должно, только сборка
  и то, что положено границе.
